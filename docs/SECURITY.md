# 1단계 권한 경계

## 세 역할

- **관리자(root):** 설치와 정책 변경만 수행. MCP 도구가 관리자를 직접 호출하는 기능은 아직 없다.
- **home-mcp:** 외부 HTTP/OAuth 처리. 작업 공간을 직접 볼 수 없는 서비스 정의이며 명령을 실행하지 않는다. 인증 DB를 소유한다.
- **home-mcp-runner:** Unix 소켓으로 전달받은 도구 실행. 별도 UID, 로그인 암호/토큰 없음, sudo/docker 추가 그룹 없음.

실행기는 커널이 알려주는 소켓 상대 UID를 확인한다. 모델의 문자열 역할/확인 플래그로 신뢰하지 않는다. 미래 root 실행기는 이 서비스와 분리하고 작업별 승인 내용을 서버에서 확인해야 한다.

## 파일과 명령

모든 파일 도구와 터미널은 bubblewrap의 새 마운트/프로세스/사용자/네트워크 환경 안에서 실행한다. 호스트 전체 `/`를 통째로 바인드하지 않는다. 호스트 `/usr` 등 실행에 필요한 런타임은 읽기 전용으로 보이고, 지정한 데이터 읽기 경로만 추가한다. `/proc`는 새 프로세스 공간이며 `/dev`도 별도로 구성한다.

지속되는 쓰기는 `/mnt/storage/dev`에 한정하고 `server` 하위는 비어 있는 읽기 전용 마운트로 가린다. 임시 `/tmp`와 임시 HOME은 별개로 쓰기 가능하지만 작업 종료 시 사라진다. 도구가 /etc/home-mcp, 인증 DB, 호스트의 /root/.ssh, Docker 소켓, 프로세스 환경을 받아 가는 구조가 아니다.

읽기 허용 목록의 기본값은 /etc/os-release, /etc/hostname이다. 다른 폴더를 전부 읽을 수 있게 열지 않는다. 관리자 정책에 추가한 경로만 확장한다. 이 읽기 권한은 그 경로를 쓰거나 root로 읽을 권한이 아니다. 읽기 경로 추가 시 토큰/개인정보 포함 여부를 관리자가 판단해야 한다.

파일 API는 경로 이탈, 구성요소 심볼릭 링크, 특수 파일, 다중 하드링크를 거부한다. 덮어쓰기는 읽어온 해시가 일치해야 하며 해시 생략은 새 파일 생성만 허용한다. 쓰기 실패·중단은 원상복구 보장이 아니며 동시 외부 편집과 충돌할 수 있다. 단일 실행기 안에서는 작업을 직렬화한다.

터미널의 안전 경계는 문자열 필터가 아니라 OS 격리다. 프로젝트 내부 명령은 파일 삭제도 할 수 있으므로 작업장 자체는 승인한 쓰기 영역이다. 임의 셸에 대해 파일 API와 동일한 심볼릭 링크 금지 규칙까지 적용했다고 주장하지 않는다. 링크를 따라가더라도 보이는 마운트와 OS 권한 안에서만 접근해야 한다.

특히 기존 작업장에 작업장 밖 파일의 하드링크가 이미 있거나 외부 관리자가 실행 중 경로·마운트를 바꾸면 경계 해석이 달라질 수 있다. 3단계 설치 검사에서 기존 하드링크/다른 서비스의 공유 쓰기 권한을 확인해야 한다. 작업장 바깥에 같은 실행 UID의 쓰기 경로를 만들지 않는다. 워크스페이스 내부의 비밀값은 임의 명령이 읽을 수 있으므로 거기에 서버 인증 정보를 보관하지 않는다. 이 소스는 미검증 상태이며 모든 파일 유출/커널 취약점까지 막는다고 보증하지 않는다.

중첩 호스트 마운트는 1단계에서 거부한다. syscall 필터로 socket/connect/전송, io_uring, ptrace, mount, unshare/setns 등 우회에 쓰일 수 있는 기능을 막는다. 따라서 작업장에 우연히 UNIX 소켓 파일이 있어도 Docker 같은 호스트 서비스에 연결하는 통로로 사용하지 못하도록 설계했다. 이 필터는 명령의 외부 통신도 차단하며, 온라인 Git/패키지 설치는 2단계에서 별도 설계한다.

## 인증

고정된 OAuth 클라이언트 하나, S256 PKCE, 정확한 콜백 URI 허용 목록, 정확한 resource 바인딩을 사용한다. 서버는 임의 client_id URL을 가져오지 않으며 DCR/CIMD를 구현한 척하지 않는다. 제공된 클라이언트 ID/secret 방식으로 연결한다.

발급자(issuer)는 SDK의 정규화에 맞춰 `https://도메인/`로 통일한다. protected-resource 메타데이터와 authorization 메타데이터, 성공/거부 콜백의 iss가 동일해야 한다. 실제 Host/Origin 및 본문 크기를 검사하고 프록시의 임의 X-Forwarded 값을 신뢰하지 않는다.

브라우저 승인에는 일회용 쿠키·CSRF 값과 설치 시 발급한 소유자 암호가 필요하다. 이 과정은 ChatGPT 로그인 자체를 구현하거나 OpenAI 구독 토큰을 복사하는 과정이 아니다. 소유자 암호는 scrypt 해시, client secret과 bearer/refresh token은 해시만 인증 DB에 보관한다. 초기 원문은 root 전용 설치 정보 파일에 잠시 남고 사용자가 보관 후 삭제한다.

access token은 최대 15분, 연결 grant는 최대 30일이며 refresh token은 사용할 때마다 교체한다. 사용한 refresh token 재사용이 감지되면 해당 연결의 토큰을 전부 폐기한다. 연결 끊김을 이유로 파일 변경·명령 실행·인증 교환을 앱이 자동 반복하지 않는다. 이 때문에 응답 유실 시 수동 재연결/실제 결과 확인이 필요할 수 있다.

## 남겨 둔 보호

단일 짧은 명령 시간 제한, 출력 크기, 요청 크기, 프로세스 수·메모리/CPU 제한, 유효한 토큰 검사, 기존 파일 해시 검사. 이는 Agent Hub에서 제거했던 '모델 왕복 호출 횟수 제한'과 다른 실행 안전장치다.

권한 상승이나 root 자동 허용은 1단계에 없다. 채팅 클라이언트의 '항상 허용'이 서버의 파일 권한을 넓히거나 미래 root 작업 승인을 대체해서는 안 된다.
